Inscription publique cassee — Actions Backend

Holy Fork | 15 septembre 2026

Probleme
  • Le frontend envoie type_employe_id: 383 en dur sur POST /api/auth/register/ (inscription publique, gerant qui cree son compte)
  • 383 est un ID auto-incremente de TypeEmploye, pas une valeur stable — il n'existe pas sur toutes les bases (confirme en local : IDs reels 25-32, 383 absent)
  • Resultat : 400 {"type_employe_id": ["Cle primaire « 383 » non valide - l'objet n'existe pas."]} — inscription impossible, et l'erreur n'est meme pas affichable proprement cote frontend (le champ n'existe pas dans le formulaire)
  • Testable en 3 lignes : voir §4

1. Rendre type_employe_id optionnel a l'inscription publique MODIFIER

UserRegistrationSerializer (apps/authentication/serializers.py) est partage par deux flux :

  • UserRegistrationView (apps/authentication/views.py, AllowAny) — inscription publique, appelee par le frontend /register. C'est le flux casse.
  • L'invitation admin (apps/settings/views.py, IsAuthenticated) — instancie le meme serializer avec context={'is_admin_invite': True}, et choisit explicitement le role de l'employe invite. Ce flux doit continuer d'exiger type_employe_id.

Rendre le champ optionnel, et resoudre "Super Admin Groupe" cote serveur quand il est absent (uniquement pour l'inscription publique) :

# apps/authentication/serializers.py — UserRegistrationSerializer

DEFAULT_SELF_REGISTER_ROLE = "Super Admin Groupe"

class UserRegistrationSerializer(serializers.ModelSerializer):
    # ... champs existants inchanges ...

    type_employe_id = serializers.PrimaryKeyRelatedField(
        queryset=TypeEmploye.objects.all(),
        required=False,   # ← etait required=True
        write_only=True
    )

    def validate(self, attrs):
        # ... validations existantes (password2, PIN unique) inchangees ...

        # L'invitation admin doit toujours choisir un role explicitement.
        # Seule l'inscription publique (self-register) peut s'en passer.
        if self.context.get('is_admin_invite') and not attrs.get('type_employe_id'):
            raise serializers.ValidationError({
                "type_employe_id": "Ce champ est obligatoire pour une invitation."
            })
        return attrs

    def create(self, validated_data):
        validated_data.pop('password2', None)
        employee_last_name = validated_data.pop('employee_last_name')
        employee_first_name = validated_data.pop('employee_first_name')
        pin_code = validated_data.pop('pin_code')
        type_employe = validated_data.pop('type_employe_id', None)
        restaurant = validated_data.pop('restaurant_id', None)

        if type_employe is None:
            # Inscription publique : le gerant qui s'inscrit doit avoir
            # tous les droits — resolu par nom, pas par un PK fige.
            type_employe = TypeEmploye.objects.get(nom_type=DEFAULT_SELF_REGISTER_ROLE)

        user = User.objects.create_user(...)  # inchange
        employe = Employe.objects.create(
            user=user,
            nom=employee_last_name,
            prenom=employee_first_name,
            pin_code=pin_code,
            type_employe=type_employe,
        )
        # ... reste inchange ...

Pourquoi resoudre par nom_type et pas par ID : TypeEmploye.nom_type a deja une contrainte unique=True (voir apps/staff/models.py) — c'est la seule valeur stable disponible sur ce modele, contrairement a l'ID auto-incremente qui varie selon l'historique de chaque base.

2. Garde-fou si le role par defaut n'existe pas RECOMMANDE

Si TypeEmploye.objects.get(nom_type="Super Admin Groupe") leve DoesNotExist (base mal seedee), retourner une erreur explicite plutot qu'un 500 :

from django.core.exceptions import ObjectDoesNotExist

if type_employe is None:
    try:
        type_employe = TypeEmploye.objects.get(nom_type=DEFAULT_SELF_REGISTER_ROLE)
    except ObjectDoesNotExist:
        raise serializers.ValidationError({
            "non_field_errors": (
                f"Configuration serveur incomplete : le role "
                f"'{DEFAULT_SELF_REGISTER_ROLE}' n'existe pas en base."
            )
        })

3. Effet de bord a verifier : type_employe_id optionnel dans le schema OpenAPI

Avanttype_employe_id requis dans UserRegistrationSerializer → present dans required: [...] du schema genere
Apresretire de required — regenerer le schema (spectacular --validate) et le publier pour que le frontend le recupere (voir doc frontend correspondante)

C'est un changement non-breaking pour l'invitation admin (elle envoie toujours le champ), et breaking pour aucun consommateur existant puisqu'on assouplit une contrainte (optionnel au lieu de requis), pas l'inverse.
